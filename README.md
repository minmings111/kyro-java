# Kyro

Kubernetes 서비스 장애 상황에서 운영자가 반복적으로 수행하는 증거 수집, 원인 후보 정리, 복구 액션 판단, 안전한 변경안 생성 과정을 하나의 흐름으로 연결하는 솔루션.

기존 프로젝트의 RCA/AI 흐름이 증상·시그널 매칭 중심으로 구현되어 있어 장애 원인 판단 과정을 충분히 구체화하지 못했다는 아쉬움이 있었고, 이를 계기로 RCA 후보 생성, 근거 평가, 복구 판단의 책임을 더 명확히 이해하고 분리하기 위해 프로젝트를 다시 정리하고 있습니다.

## 왜 Java로 다시 만들었나

기존 프로젝트는 빠르게 기능을 검증하기 위해 Python 중심으로 여러 워커, 이벤트, GitOps 흐름을 구성했습니다. Python은 아이디어를 빠르게 구현하고 검증하기에는 좋았지만, Kyro처럼 장애 분석, 복구 판단, 변경 생성이 여러 모듈을 오가며 이어지는 백엔드에서는 점점 책임 경계가 흐려지는 문제가 있었습니다.

Python으로도 충분히 구조화된 코드를 만들 수 있지만, 기본 언어 특성상 책임 경계를 강제하기보다 개발자의 규칙과 팀의 관례에 맡기는 부분이 많았습니다. 예를 들어 `_private` 네이밍은 실제 접근을 막지 않고, module-level 변수나 dictionary 형태의 데이터는 여러 계층에서 쉽게 참조되거나 변경될 수 있습니다. 타입 힌트도 런타임 계약을 직접 강제하지 않기 때문에, 이벤트 payload나 서비스 간 인터페이스가 커질수록 잘못된 값 전달이 실행 시점까지 드러나지 않을 수 있다고 느꼈습니다.

이러한 문제는 Java의 접근 제어자, 인터페이스, record, 패키지 구조, 생성자 기반 의존성 주입을 활용해 책임과 계약을 코드 레벨에서 명시하는 방식으로 개선할 수 있다고 판단했습니다. 객체의 책임, 계층 간 데이터 전달 범위, 모듈 간 계약이 코드 구조 안에서 더 분명하게 드러나도록 Kyro를 Java/Spring Boot 기반으로 재구조화하기로 결정했습니다.

## 현재 구현 범위

- Kubernetes 장애 증거 수집부터 RCA, 복구 액션 선택, Safe PR 생성까지 이어지는 핵심 백엔드 흐름을 모듈 단위로 구성

## 기술적 고민

### 모듈형 모놀리스와 확장성

처음부터 분산 시스템으로 만들면 메시징, 배포, 장애 처리 복잡도가 먼저 커질 수 있습니다. 그래서 현재는 모듈형 모놀리스로 도메인 경계를 선명하게 만들고, 실제 병목이나 독립 배포 필요가 확인된 모듈만 외부 서비스로 분리하기로 결정하였습니다.
